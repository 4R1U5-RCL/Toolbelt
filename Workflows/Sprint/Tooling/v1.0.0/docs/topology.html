Parallel session fleet — how the pieces talk

One orchestrator, one reviewer, and N workers run as separate Claude Code terminals. They coordinate through two shared surfaces: a file mailbox for messages and a canonical doc in a git worktree for durable state. Neither depends on peer session-registration — which is exactly what was failing.

Figure 1 — Spin-up & delegation

The sprint opens as a plan → draft → delegate → work sequence. You prompt twice — once to plan, once to hand each worker its task — and those two prompts are the human gate around the autonomous loop.

Figure 2 — Live transport

Every message crosses the scratch mailbox, addressed by a stable logical name. No session has to resolve another session's studio-XX id.

Figure 3 — Durable state

Messages are transient. The canonical board is the memory: one doc, one writer, many readers — living in an isolated git worktree the whole fleet shares.

How one work unit moves

  1. Assign. You post a worker its task. orchestrator appends the §3 row + §4 summary to SPRINT.md
  2. Work. The worker reads the board, does the task inside the worktree, pings STATE → orchestrator inbox
  3. Submit. Worker drops a packet → reviewer inbox (TASK · WHERE · WHAT · VERIFIED · NOT DONE)
  4. Verify. Reviewer drains its inbox, checks against the §4 acceptance criteria, writes a verdict → worker inbox
  5. Resolve. COMPLETE → worker reports out + STATE-pings; NEEDS ITERATION → fix BLOCKER/HIGH, resubmit ROUND 2
  6. Record. Orchestrator folds the verdict into SPRINT.md — status flips to COMPLETE, outcome written.
fallback = reliable path   Transport lives in scratch/ (gitignored, shared filesystem); the board lives in the worktree.
